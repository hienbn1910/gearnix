# W1-04 — Xử lý lỗi, validation và tài liệu API

## 1. Mục tiêu

Mọi lỗi API trả về có **một hình dạng duy nhất**: ProblemDetails kèm `code` (mã ổn định để frontend hiển thị câu
tiếng Việt) và `traceId` (để tìm trong log). Task này còn làm 3 việc:
- Nối FluentValidation để mọi request body tự được kiểm tra trước khi vào controller.
- Tạo kiểu Result cho lỗi nghiệp vụ và các kiểu dữ liệu chung cho danh sách.
- Bật tài liệu API (OpenAPI và Scalar).

- Spec: issue [#12](https://github.com/hienbn1910/gearnix/issues/12)
- PR: là PR có dòng `Closes #12`

## 3. Kiến thức

- **ProblemDetails (RFC 9457):** định dạng JSON chuẩn cho lỗi HTTP: `type`, `title`, `status`, `detail`, cộng thêm các
  trường mở rộng (extension), ở đây là `code` và `traceId`. Content-type là `application/problem+json`.
- **Middleware pipeline:** chuỗi các bước mà mỗi request đi qua. Thứ tự quan trọng:
  - `UseExceptionHandler()` đứng **ngoài cùng**, để bắt được exception từ mọi bước phía trong.
  - `UseStatusCodePages()` gắn body cho các response lỗi không có body, ví dụ route không tồn tại.
- **`IExceptionHandler`:** cách của .NET 8 trở lên để xử lý exception tập trung. Exception được ghi vào log
  (phía server), còn client chỉ nhận một câu chung chung.
- **`IsTransient` của Npgsql:** cờ đánh dấu lỗi "thử lại có thể được". Nhưng nó gộp cả deadlock (`40P01`) và
  serialization failure (`40001`). Hai lỗi này **code phải tự thử lại** (§11.3), không phải "database sập". Vì vậy tôi
  tự viết luật, dựa trên SQLSTATE (mã lỗi 5 ký tự của PostgreSQL):
  - **`503`:** lỗi kết nối, lớp `08` (kết nối), lớp `53` (thiếu tài nguyên), `57P01`–`57P03` (server đang tắt hoặc
    khởi động).
  - **Còn lại → `500`.**
- **Kiểu Result:** thay vì `throw new OutOfStockException()`, service trả `Result<T>`, chứa giá trị hoặc `Error`.
  - Lỗi nghiệp vụ là chuyện **bình thường**, không phải bất thường. Exception vừa chậm vừa ẩn luồng điều khiển.
  - `[MemberNotNullWhen]`: báo cho trình biên dịch biết "khi `IsSuccess` là false thì `Error` chắc chắn khác null",
    nên không cần dấu `!`.
- **Action filter:** đoạn code chạy trước và sau mỗi action. Filter validation tìm `IValidator<T>` theo **kiểu lúc chạy**
  của từng tham số (`MakeGenericType`), nên mọi DTO có validator đều tự được kiểm tra.
- **`[ApiController]`:** khi ModelState lỗi (ví dụ JSON hỏng), nó tự trả `400` trước khi filter của mình chạy. Cấu hình
  ProblemDetails dùng chung nên `400` này cũng có `code` và `traceId`.
- **`AllowInputFormatterExceptionMessages = false`:** mặc định, lỗi đọc JSON trả kèm thông báo của System.Text.Json, có
  cả tên type nội bộ (`Gearnix.Api...`). Tắt đi để không lộ cấu trúc code.
- **`JsonStringEnumConverter`:** enum ra JSON dạng chuỗi. Phải đăng ký ở 2 nơi:
  - JSON options của MVC: cho request và response của controller.
  - `ConfigureHttpJsonOptions`: để tài liệu OpenAPI cũng mô tả enum dạng chuỗi.
- **OpenAPI và Scalar:** OpenAPI là bản mô tả API mà máy đọc được (W1-09 sẽ sinh kiểu TypeScript từ nó). Scalar là trang
  web hiển thị bản mô tả đó và cho gọi thử API.
- **Application part:** cơ chế để ASP.NET Core tìm controller trong một assembly khác. Test dùng nó để gắn
  `TestErrorsController` vào API mà code thật không bị ảnh hưởng.

## 4. Quyết định và lý do

| Quyết định | Phương án khác | Vì sao chọn |
|---|---|---|
| Kiểu Result cho lỗi nghiệp vụ | Ném exception rồi bắt ở middleware | Rule.md §7; luồng lỗi hiện rõ trong chữ ký hàm; không tốn chi phí exception |
| Tự viết action filter validation | Gói `FluentValidation.AspNetCore` | Gói đó đã bị tác giả ngừng khuyến nghị; filter khoảng 50 dòng, giải thích được |
| `code` ổn định, câu chữ tiếng Anh | Trả câu tiếng Việt từ API | Frontend tự dịch theo `code`; đổi câu chữ không làm hỏng client |
| Mã dự phòng `bad_request`, `service_unavailable`, `conflict` | Mọi status lạ → `internal_error` | `415` (lỗi của client) không được bị báo là "lỗi server" |
| Deadlock → `500` | Theo `IsTransient` → `503` | Deadlock phải được code tự thử lại; nếu lọt ra ngoài thì đó là bug |
| Controller chỉ có trong test | Thêm endpoint test vào code thật | Code thật không chứa đường dẫn nào chỉ để test |
| Tài liệu API chỉ bật ở Development và Demo | Bật ở mọi môi trường | Demo để nhà tuyển dụng xem; Test và LoadTest không cần |

## 6. Câu hỏi phỏng vấn

1. **"Tại sao trả Result thay vì ném exception cho lỗi nghiệp vụ?"**
   - Gợi ý: hết hàng là chuyện **dự kiến được**, không phải bất thường.
   - Result làm luồng lỗi hiện rõ trong chữ ký hàm, nên người gọi buộc phải xử lý.
   - Exception tốn chi phí, và dễ bị bắt nhầm chỗ.
   - Exception chỉ dành cho lỗi thật (bug, database sập).
2. **"Làm sao đảm bảo API không lộ thông tin nội bộ khi lỗi?"**
   - Gợi ý: một `IExceptionHandler` trả câu chung chung, còn chi tiết chỉ ghi vào log.
   - Tắt thông báo lỗi của JSON serializer.
   - Có test khẳng định body không chứa message của exception hay tên type.
   - Muốn tìm lỗi thì dùng `traceId`.
3. **"Database sập thì API trả gì? Deadlock thì sao?"**
   - Gợi ý: lỗi kết nối hoặc server quá tải → `503 database_unavailable`, client có thể thử lại sau.
   - Deadlock thì code phải tự thử lại cả transaction; nếu vẫn lọt ra ngoài thì đó là bug → `500`.
   - Vì vậy tôi không dùng thẳng `IsTransient` của Npgsql.

## 7. Lưu ý

- `[ApiController]` trả `400` cho lỗi đọc JSON **trước khi** filter chạy. Key trong `errors` lúc đó do framework đặt
  (ví dụ `$.kind`), không phải camelCase của mình. Khi có endpoint danh sách đầu tiên (W1-07), kiểm tra key cho lỗi
  query, ví dụ `?page=abc`.
- Scalar trả `302` từ `/api/docs` sang `/api/docs/`. `HttpClient` tự đi theo chuyển hướng nên test thấy `200`.
- Tham số `count` của `str.replace` trong Python là số nguyên, không phải chuỗi. Một script sửa file đã chạy dở
  vì lỗi này: luôn kiểm tra kết quả sau khi sửa hàng loạt.
- Test chạy ở môi trường Development sẽ đọc user-secrets của máy. Chỉ chuỗi kết nối được test đặt cố định.
- **Việc sau này:**
  - `429` thật đến từ rate limiter ở W4-06; nhớ đặt `RejectionStatusCode = 429` (mặc định là `503`).
  - `401`/`403` thật đến ở W1-05.
