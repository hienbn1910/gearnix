# W1-03 — Nền tảng dữ liệu và endpoint health

## 1. Mục tiêu

Đặt nền cho mọi phần làm việc với database sau này. Gồm:
- `AppDbContext` dùng chung cho mọi module, với các quy ước: tên `snake_case`, tiền `numeric(18,2)`, thời gian UTC.
- Cấu hình kết nối được kiểm tra ngay khi khởi động.
- `TimeProvider` là nguồn thời gian duy nhất.
- Migration đầu tiên.
- Hai endpoint `/api/health/live` và `/api/health/ready`.

Đây cũng là task có **test đầu tiên** của dự án, nên CI đã bỏ được tùy chọn tạm `--ignore-exit-code 8`.

- Spec: issue [#10](https://github.com/hienbn1910/gearnix/issues/10)
- PR: là PR có dòng `Closes #10`

## 3. Kiến thức

- **`DbContext`:** đối tượng của EF Core đại diện cho một "phiên làm việc" với database. Nó theo dõi entity, sinh SQL và
  mở transaction. Dự án chỉ có **một** `AppDbContext`, nên một transaction có thể bao nhiều module (§5.3).
- **Scoped lifetime:** `AddDbContext` đăng ký `AppDbContext` kiểu *scoped*: mỗi request HTTP nhận một instance riêng.
  - Không được tiêm một service scoped vào một singleton (service sống suốt đời ứng dụng). Nếu làm vậy, mọi request
    sẽ dùng chung một `DbContext`, mà `DbContext` không an toàn khi dùng song song.
- **Convention (quy ước) của EF:** luật áp cho **cả mô hình**, không phải cho từng cột.
  - `ConfigureConventions`: mọi `decimal` → `numeric(18,2)`.
  - `UseSnakeCaseNamingConvention()` (package EFCore.NamingConventions): `UnitPrice` → `unit_price`.
- **`DateTimeOffset` và `timestamptz`:** Npgsql (driver PostgreSQL cho .NET) tự lưu `DateTimeOffset` thành
  `timestamptz` và **từ chối** giá trị có offset khác 0. Vì vậy quy ước UTC do Npgsql đảm nhận, không cần viết code
  riêng. `TimeProvider.GetUtcNow()` cũng trả về đúng `DateTimeOffset` UTC.
- **Options pattern:** cấu hình (từ appsettings, user-secrets, biến môi trường) được gắn vào một class C#.
  - `[Required]`, `[Range]` là luật kiểm tra.
  - `ValidateOnStart()` kiểm tra **ngay khi khởi động**: thiếu chuỗi kết nối thì API dừng luôn, kèm thông báo
    rõ ràng, chứ không đợi tới request đầu tiên mới lỗi.
- **Connection pool:** Npgsql giữ sẵn tối đa `MaxPoolSize` (50) kết nối để dùng lại, vì mở kết nối mới rất tốn.
  - `Timeout` (15 giây) là thời gian tối đa để **lấy được** một kết nối, dù là chờ kết nối rảnh hay mở kết nối mới.
  - PostgreSQL cho tối đa 100 kết nối, nên 50 vẫn chừa chỗ cho migration, backup và công cụ quản trị.
- **User-secrets:** kho bí mật của .NET cho máy dev, nằm ở `~/.microsoft/usersecrets/<UserSecretsId>/`, ngoài repo.
  Chỉ được đọc ở môi trường `Development`. `UserSecretsId` trong `.csproj` chỉ là một mã định danh, không phải bí mật.
- **Health check: liveness và readiness:**
  - **Liveness** (`live`): "process còn sống không?". Không kiểm tra gì cả. Docker dùng nó để quyết định có khởi động
    lại container hay không. Nếu `live` có kiểm tra database, database sập sẽ làm Docker khởi động lại API mãi, mà vô ích.
  - **Readiness** (`ready`): "phục vụ được request chưa?". Có kiểm tra database. Uptime monitor và bước deploy dùng nó.
  - Unhealthy → `503 Service Unavailable` (mặc định của ASP.NET Core).
  - Mỗi lần kiểm tra có giới hạn 3 giây, để `ready` không bị treo cả 15 giây chờ pool.
- **Migration:** file C# mô tả cách thay đổi schema. Có `Up` (áp dụng) và `Down` (hoàn tác).
  - EF lưu các migration đã chạy trong bảng `__EFMigrationsHistory`.
  - Migration **không** chạy lúc khởi động ứng dụng (Rule.md §10). Ở máy dev, chạy bằng `dotnet ef database update`.
    Khi deploy, chạy bằng migration bundle (W5-03).
- **Local tool (`.config/dotnet-tools.json`):** công cụ `dotnet` được ghim phiên bản theo từng repo.
  - `dotnet tool restore` cài đúng bản đó.
  - Bản ghim theo repo được ưu tiên hơn bản cài toàn máy (máy bạn có `dotnet-ef` 11.x cài toàn máy).
- **`WebApplicationFactory`** (package Microsoft.AspNetCore.Mvc.Testing): chạy toàn bộ API trong bộ nhớ của test.
  `CreateClient()` trả về một `HttpClient` gọi thẳng vào API, không cần mở cổng mạng.
- **Testcontainers:** thư viện bật container Docker thật từ code test. Ở đây là `postgres:17`, giống hệt
  docker-compose. Test chạy trên PostgreSQL thật nên bắt được những lỗi mà database giả trong bộ nhớ sẽ bỏ qua.
- **Assembly fixture (xUnit v3):** "đồ dùng chung" tạo **một lần** cho cả project test. Container khởi động khoảng
  vài giây, nên dùng chung thay vì mỗi test bật một container.

## 4. Quyết định và lý do

| Quyết định | Phương án khác | Vì sao chọn |
|---|---|---|
| Tự viết health check (`CanConnectAsync`) | Package HealthChecks.EntityFrameworkCore | Khoảng 10 dòng, không thêm phụ thuộc, giải thích được từng dòng |
| `live` không kiểm tra gì | `live` cũng kiểm tra database | Database sập không phải lý do để Docker khởi động lại API |
| Đường dẫn `/api/health/...` | `/health/...` | Caddy chỉ chuyển `/api` vào API; uptime monitor ở ngoài phải gọi được |
| Gắn pool vào chuỗi kết nối bằng code | Ghi sẵn trong chuỗi kết nối | Cấu hình ở một chỗ, có kiểm tra giá trị (1–100, 1–60 giây) |
| `DateTimeOffset` | `DateTime` với `Kind = Utc` | Khớp với `TimeProvider.GetUtcNow()`; Npgsql từ chối giá trị không phải UTC |
| Ở lại .NET 10 LTS, ghim package 10.x | Lên .NET 11 | LTS được hỗ trợ lâu; đổi phiên bản giữa dự án là rủi ro không cần thiết |
| Migration chạy trong fixture test | Chạy lúc khởi động ứng dụng | Rule.md §10 cấm migrate lúc khởi động; fixture vẫn chứng minh migration chạy được |
| Test quy ước bằng entity mẫu chỉ có trong test | Chờ W1-06 có entity thật | Bảo vệ invariant "tiền là `decimal`" ngay từ bây giờ, và project UnitTests có test |
| `Down()` để trống (không xóa `pg_trgm`) | `DROP EXTENSION` khi hoàn tác | EF sinh như vậy; hoàn tác không bao giờ phá dữ liệu hay index tìm kiếm |

## 5. Test

| Test | Kiểm tra gì | Vì sao cần |
|---|---|---|
| `Model_SampleEntity_UsesSnakeCaseNames` | Bảng `sample_order`, cột `unit_price`, `created_at` | Quy ước đặt tên áp cho mọi entity sau này |
| `Model_DecimalProperty_MapsToNumeric18And2` | `decimal` → `numeric(18,2)` | Bảo vệ invariant số 9: tiền không bao giờ sai độ chính xác |
| `Model_DateTimeOffsetProperty_MapsToTimestamptz` | `DateTimeOffset` → `timestamp with time zone` | Thời gian luôn lưu kèm múi giờ (UTC) |
| `Live_DatabaseUnreachable_Returns200` | `live` trả `200` khi database **không** truy cập được | Chứng minh `live` không đụng database, và API vẫn khởi động khi database sập |
| `Ready_DatabaseReachable_Returns200` | `ready` trả `200` với PostgreSQL thật | Trường hợp bình thường |
| `Ready_DatabaseUnreachable_Returns503` | `ready` trả `503` khi không có database | Uptime monitor phải báo động được |
| `Start_ConnectionStringMissing_FailsWithValidationError` | Thiếu chuỗi kết nối → `OptionsValidationException` | `ValidateOnStart` thật sự hoạt động |

- **Mutation check:** test `ready → 503` xanh ngay từ đầu, nên tôi tạm làm hỏng code (bỏ kiểm tra database). Test
  chuyển đỏ (`Expected: ServiceUnavailable, Actual: OK`). Vậy test thật sự bắt được lỗi.
- **Chống "rò" cấu hình:** factory luôn đặt chuỗi kết nối, kể cả chuỗi rỗng. Đã thử chạy với biến môi trường
  `Database__ConnectionString` có giá trị: test vẫn xanh.

## 6. Câu hỏi phỏng vấn

1. **"Liveness và readiness khác nhau thế nào? Sao `live` không kiểm tra database?"**
   - Gợi ý: `live` trả lời "có cần khởi động lại process không?". `ready` trả lời "có nhận traffic được không?".
   - Nếu `live` kiểm tra database, database sập sẽ khiến Docker khởi động lại API liên tục mà không sửa được gì.
2. **"Ứng dụng phản ứng thế nào khi thiếu cấu hình, và khi database sập?"**
   - Gợi ý: thiếu chuỗi kết nối thì dừng ngay khi khởi động (`ValidateOnStart`), vì cấu hình sai thì nên lỗi sớm.
   - Database sập thì API **vẫn chạy**, vì lúc khởi động không làm việc gì với database. `ready` trả `503` để
     monitor báo động, và API tự phục hồi khi database lên lại.
3. **"Tại sao integration test dùng PostgreSQL thật thay vì InMemory database?"**
   - Gợi ý: InMemory không có transaction, constraint, `numeric(18,2)`, `timestamptz` hay extension.
   - Các bài toán cốt lõi (atomic update, unique constraint, đồng thời) chỉ kiểm được trên database thật.
   - Testcontainers bật container thật, mỗi lần chạy test là một database sạch.

## 7. Lưu ý

- **`--environment` của `dotnet run`:** khi chạy `dotnet run --no-launch-profile --environment Development`, ứng dụng
  không đọc được user-secrets. Đặt `ASPNETCORE_ENVIRONMENT=Development` thì chạy đúng. Bình thường chỉ cần
  `dotnet run --project src/Api`: profile `http` đã đặt sẵn môi trường Development.
- `user-secrets init` tự chèn BOM vào `.csproj`, đã xóa đi.
- **Thư viện đổi API:** `new PostgreSqlBuilder()` (không tham số) đã bị đánh dấu lỗi thời ở Testcontainers 4.17. Phải
  dùng `new PostgreSqlBuilder("postgres:17")`, vì `TreatWarningsAsErrors` biến cảnh báo thành lỗi build.
- Với kiểu tham chiếu, `Assert.NotNull` của xUnit v3 **không** trả về giá trị. Gọi nó trước, rồi trình biên dịch tự hiểu
  biến không còn null.
- Bảng `__EFMigrationsHistory` cũng bị đổi tên cột sang `snake_case` (`migration_id`). Không sao, miễn là quy ước luôn bật.
- **Việc sau này:**
  - Body `503` dạng ProblemDetails cho các endpoint API thuộc W1-04.
  - `FakeTimeProvider` dùng khi có logic phụ thuộc thời gian.
