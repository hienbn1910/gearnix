# W1-02 — CI với GitHub Actions và Dependabot

## 1. Mục tiêu

Mỗi pull request vào `main` được máy của GitHub tự kiểm tra: build, format, test và lỗ hổng thư viện. Kết quả hiện
thành dấu ✅/❌ ngay trên PR. Dependabot tự mở PR mỗi tuần khi có phiên bản thư viện mới.

- Spec: issue [#8](https://github.com/hienbn1910/gearnix/issues/8)
- PR: là PR có dòng `Closes #8`

## 2. Đã làm gì

| File | Vai trò |
|---|---|
| `.github/workflows/ci.yml` | Workflow CI: một job `backend` gồm restore → build Release → kiểm tra format → test → kiểm tra lỗ hổng |
| `.github/dependabot.yml` | Dependabot theo dõi NuGet và GitHub Actions hằng tuần; bản nhỏ gom 1 PR, bản lớn tách riêng |
| `README.md` | Badge trạng thái CI ở đầu trang |
| `Workflow.md`, `Workflow.vi.md` | Tick W1-01, gắn #8 cho W1-02, sửa câu về điều kiện chạy CI, nhắc W1-03 gỡ tùy chọn tạm |
| `Rule.md` §1 | Ngoại lệ: commit của Dependabot dùng `chore(deps)` và không có số issue |

## 3. Kiến thức

- **CI (Continuous Integration — tích hợp liên tục):** mỗi lần có thay đổi, một máy chủ tự chạy build và test.
  Lỗi bị phát hiện trước khi merge chứ không phải sau.
- **GitHub Actions:** dịch vụ CI có sẵn của GitHub, miễn phí cho repo public.
  - **Workflow:** file YAML trong `.github/workflows/`.
  - **Job:** một nhóm bước chạy trên một máy ảo (runner), ở đây là `ubuntu-latest`.
  - **Step:** một lệnh shell (`run:`) hoặc một action có sẵn (`uses:`).
- **Trigger (`on:`):** sự kiện làm workflow chạy. Ở đây là `pull_request` vào `main` và `push` lên `main`.
- **`permissions: contents: read`:** token mà workflow nhận chỉ được đọc repo (nguyên tắc quyền tối thiểu).
- **`concurrency` + `cancel-in-progress`:** push thêm commit vào PR thì lần chạy cũ bị hủy.
- **Mã thoát (exit code):** 0 là thành công, khác 0 là thất bại. CI dựa vào mã thoát để tô xanh hay đỏ.
  - Microsoft.Testing.Platform trả mã **8** khi "không có test nào chạy".
  - `--ignore-exit-code 8` coi riêng mã 8 là thành công. Đây là tùy chọn tạm, W1-03 sẽ gỡ.
- **Lỗ hổng package và advisory:** lỗ hổng đã công bố được ghi thành advisory (ví dụ `GHSA-5crp-9r3c-p9vr`).
  - **Package gián tiếp (transitive):** package mà package của mình kéo theo. Lỗ hổng cũng hay nằm ở đây.
- **NuGet Audit:** từ .NET 8, `dotnet restore` tự đối chiếu package với danh sách advisory và báo `NU1901`–`NU1904`.
  Nếu không lấy được dữ liệu thì báo `NU1900`. Có `TreatWarningsAsErrors`, các cảnh báo này thành **lỗi restore**.
- **Dependabot:** bot của GitHub, tự mở PR nâng phiên bản. `groups` gom nhiều bản cập nhật vào 1 PR.
- **Badge:** ảnh SVG do GitHub tạo, luôn hiện trạng thái mới nhất của workflow trên `main`.
- **Ruleset (bảo vệ branch):** quy tắc GitHub cho `main`: bắt buộc check `backend` xanh, cấm push thẳng.

## 4. Quyết định và lý do

| Quyết định | Phương án khác | Vì sao chọn |
|---|---|---|
| Chạy CI khi có PR vào `main` và push lên `main` | Chạy mọi lần push | Tránh mỗi PR chạy 2 lần; PR bắt buộc nên không bỏ sót |
| Một job `backend`, build Release | Nhiều job song song | Mỗi job phải restore và build lại; Release giống lúc deploy |
| `--ignore-exit-code 8` tạm thời | Test giả `Assert.True(true)`; làm W1-03 trước | Test giả vô nghĩa; đổi thứ tự thì W1-03 không có CI |
| Đọc JSON để báo lỗi lỗ hổng | Chỉ chạy lệnh liệt kê | Lệnh liệt kê luôn trả 0, CI sẽ không bao giờ đỏ |
| Action theo tag lớn (`@v7`) | Ghim mã commit SHA | Dễ đọc; Dependabot theo dõi cập nhật; đủ cho portfolio |
| Chưa cache NuGet | Cache + lock file | Restore mất vài giây; lock file thêm việc mỗi lần đổi package |
| Tiền tố `chore(deps)` cố định | `chore` + `include: scope` | `include: scope` có thể sinh `chore(deps-dev)` |

## 5. Test

Task này không có test C#. Phần "test" là chứng minh CI làm đúng việc của nó:

- **Chạy lại các lệnh CI ở máy local:** build Release (0 warning), format (mã 0), test (mã 8 nếu không có tùy chọn,
  mã 0 nếu có). Mục đích: biết chắc CI xanh không phải do may mắn.
- **Thử bước kiểm tra lỗ hổng bằng project tạm, nằm ngoài repo:**
  - Có Newtonsoft.Json 12.0.1 (lỗ hổng mức High): mã thoát 1, CI đỏ.
  - Gỡ package ra: mã 0, CI xanh.
  - Mục đích: chứng minh bước kiểm tra **có thể** báo đỏ. Một bước kiểm tra không bao giờ đỏ là vô dụng.
- **Thử nguồn package không truy cập được:**
  - Kết quả: lệnh liệt kê vẫn trả 0 với báo cáo rỗng.
  - Kết luận: không thể chỉ dựa vào lệnh này. Lớp bảo vệ thật nằm ở restore (NuGet Audit cộng warnings-as-errors).
    Đã thử: restore với package có lỗ hổng dừng ở mã 1.
- **CI thật trên PR:** check `backend` phải xanh. Đây là điều kiện "xong" của task.

## 6. Câu hỏi phỏng vấn

1. **"CI của bạn kiểm tra những gì, theo thứ tự nào?"**
   - Gợi ý: restore → build Release (warning = lỗi) → format → test → lỗ hổng.
   - Bước rẻ chạy trước để báo lỗi sớm.
2. **"Làm sao bạn biết bước kiểm tra lỗ hổng hoạt động?"**
   - Gợi ý: đã cố tình thêm package có lỗ hổng để thấy nó đỏ, rồi gỡ ra để thấy nó xanh.
   - `dotnet list package --vulnerable` luôn trả 0, nên phải đọc output JSON.
   - Restore cũng chặn nhờ NuGet Audit cộng `TreatWarningsAsErrors`.
3. **"Tại sao `permissions: contents: read`?"**
   - Gợi ý: nguyên tắc quyền tối thiểu.
   - Nếu một action bên thứ ba bị chiếm, nó cũng không thể push code hay sửa repo.
   - Đây cũng là lý do Dependabot theo dõi phiên bản action.
